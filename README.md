# 蓝调勘景仪 Blue Hour Scout

给短片拍摄用的蓝调时刻勘景工具。纯前端，无框架、无构建步骤、无后端。
在 iPhone 上通过「添加到主屏幕」当 App 用。

主要使用场景：Blackmagic Pyxis 6K，悉尼。

## 跑测试

### 方式一：直接打开（最快）

用浏览器打开 `test.html` 即可，结果会立刻显示在页面上。

项目刻意使用**经典 `<script>` 标签 + 全局命名空间**，而不是 ES modules，
就是为了让 `file://` 直接打开也能工作（ES modules 在 `file://` 下会被 CORS 拦掉）。

注意：Safari 对 `file://` 的子资源策略比 Chrome 严格，如果页面空白就改用方式二。
另外 Geolocation 和 DeviceOrientation 无论如何都需要 HTTPS，`file://` 下拿不到，
但测试页不需要这两样。

### 方式二：本地静态服务

```bash
cd "/Users/gongzihan/Iphone Tool" && python3 -m http.server 8765 --bind 127.0.0.1
```

然后打开 <http://localhost:8765/test.html>。

### 方式三：命令行（不开浏览器）

macOS 自带 JavaScriptCore，可以直接跑，不需要装 Node：

```bash
cd "/Users/gongzihan/Iphone Tool" && cat js/core/*.js js/data/records.js js/data/settings.js js/data/weather.js js/ui/theme.js js/ui/compass.js js/ui/app.js js/ui/viewfinder.js js/ui/horizon-ui.js js/test/harness.js js/test/*.test.js > /tmp/bh-tests.js && echo 'BH.Test.textReport(BH.Test.run());' >> /tmp/bh-tests.js && osascript -l JavaScript /tmp/bh-tests.js
```

测试文件用通配符，以后加了新的 `*.test.js` 不用改命令；但被测模块要逐个列出，
新测试依赖了新模块就得加进来。这条命令之前就漏过 `records.js` 等几个依赖，
跑出来是「13 个测试直接抛错」——幸好测试框架已经修成会把抛错计入失败，
否则它会静默报全绿。

命令行没有 DOM，需要真实布局的测试（准星几何、主题对比度、输入组件）会跳过，
所以命令行是 1121 条，浏览器里是 1232 条。

## 在电脑上测罗盘（模拟器）

Mac 没有磁力计，罗盘的**真值**只能在手机上验。但采样**交互**——自动落点、
停留进度、扇区填充、转多快才跟得上——完全可以在电脑上先跑一遍，
所以项目里内置了一个罗盘模拟器。

**网址后面加 `?sim=1` 就出现**，平时完全不干活：

```
http://localhost:8765/index.html?sim=1
```

屏幕下方会出现一个红标的「罗盘模拟器」面板：

- 两个滑块分别是方位角和仰角，拖动就相当于转动/俯仰手机
- **「自动扫一圈」**按一条假天际线（西边一排高楼、东边开阔）自动转，
  转速可选 6 / 12 / 25 / 45 度每秒
- 读数带 ±0.8° 的抖动，顺带把平滑和中位数那条路径也跑到

它直接往 window 派发合成的 `deviceorientation` 事件，`compass.js` 一行都没改——
收到的和真机上一模一样，连权限流程都会走一遍（模拟器会把 `requestPermission()`
短路成 granted，这样电脑上点「启用罗盘」也能走通）。

这个模拟器上线后抓到了三个真问题：转速超过 18°/秒 一个扇区都采不到而且
界面不解释、连续落点会把防抖存盘无限推迟导致中途锁屏全丢、以及转太快时
缺少提示。现在这三条都修了，也都可以用模拟器复现验证。

去掉网址里的 `?sim=1` 即可关闭。

## 功能一：勘景记录

到现场新建一条记录，存下：GPS 坐标、机位朝向方位角、**地平线遮挡剖面**、
一张参考照片、地点名称和备注。记录可查看、编辑、删除，可导出为 JSON。

数据全部存在本机 IndexedDB，照片以 Blob 单独存放。导出的 JSON 不含照片
（体积会失控），导出文件里用 `hasPhoto` 标明原记录有照片。

### 界面是分步的，不是一张长表单

```
列表  →  概览（四行，每行显示完成状态）
           ├─ 第 1 步  地点与坐标     名称 + 一键定位（时区折叠）
           ├─ 第 2 步  机位朝向       大读数 + 读罗盘（罗盘校正折叠）
           ├─ 第 3 步  地平线剖面     相机取景器 + 准星，罗盘玫瑰看覆盖
           └─ 第 4 步  照片与备注     可选
```

新建时直接进第 1 步，一路「下一步」走完；老记录从概览跳进任意一步。
每一步只做一件事，相关的两件才合并（名称和坐标、照片和备注）。
**每一步都控制在一屏之内**——第一版是一张 2.2 屏的长表单，
现场单手滚来滚去很难用。

概览页顶部直接告诉你「还差几项、缺什么」，底部只有一个主按钮
「继续：<下一个未完成项>」，不用自己判断下一步该点哪。
删除记录挪到了概览页最底下，不再和返回箭头一样挂在右上角。

### 配色的对比度

背景接近纯黑、强调色用琥珀，是为了不破坏暗适应。但第一版把次要文字
压到了 `#6b6459`，相对背景只有 **3.44:1**，低于 WCAG AA 要求的 4.5:1，
还用在 12px 上——黄昏户外根本看不清。现在三档文字色分别是
**14.8 / 6.5 / 4.8 : 1**，都过 AA，背景仍然是近黑、没有亮色块。
正文字号也从 15px 提到 16px。

### 地平线遮挡剖面怎么采

这是整个工具最关键的一步——它决定真正的日落时刻，和天文日落往往差十几分钟。

**竖着举起手机，像拍照一样用背面（后摄）对准天际线，然后原地缓慢转一圈。**

瞄准轴定义成设备的 −z 轴（后摄朝向），这么定有两个好处：手机立起来
（beta≈90°）时瞄的正好是水平方向，姿势自然；而且瞄准轴固定在机身上，
横握竖握都对，不需要做屏幕方向补偿。仰角由完整的旋转矩阵算出：

```
仰角 = asin( −cos(beta) · cos(gamma) )
```

这个式子与 alpha 无关，所以就算方位角拿不到（没有磁力计），俯仰依然准确；
`gamma` 项让手机歪一点也不影响读数。

### 相机取景器

采集时可以打开后摄预览，画面正中一个准星，把准星压在天际线上再读数。
不开相机的话，手机背面对着哪儿全靠手感，读数会很不一致。

**准星为什么是精确的，不是近似**：采样的瞄准轴定义为设备 −z 轴，也就是
后摄光轴；而预览画面的正中心就是光轴方向。两者天然重合。画面用
`object-fit: cover` 填充容器，cover 是**居中**裁切，所以不管容器什么比例，
画面中心始终是光轴。后摄物理上偏离机身中心一两厘米，但天际线在几百米
到几公里外，折算成角度远小于 0.01°，可以忽略。

注意：仰角仍然来自加速度计，不是从图像里算出来的。相机只负责让你看见
自己对准了哪儿。

几个细节：

- 罗盘和相机两个权限**必须在同一次点击里发起**。先 `await` 罗盘权限再去要
  相机的话，用户手势已经过期，iOS 会拒掉第二个。所以「启用罗盘和相机」
  一个按钮同时发起两个请求。
- `<video>` 必须带 `playsinline`，否则 iOS 会强制全屏播放；必须 `muted`
  才能自动播放。
- 加到主屏幕的独立窗口里 `getUserMedia` 需要 **iOS 14.3+**，更早的版本只有
  Safari 里能用。拿不到相机时整个功能降级，采集本身照常可用。
- 离开页面时必须停掉 MediaStream 的轨道，否则相机指示灯会一直亮着。
- 有个「相机：开/关」开关，长时间采集想省电可以关掉。

测试里有一条几何断言守着这件事：准星中心、水平参考线、进度环三者的中心
必须和画面中心重合（容差 1.5px），偏了就测试失败。

### 采样节奏

每 10° 一个扇区，共 36 个。在一个方向停住约半秒就自动记下该方向的仰角，
罗盘图上对应的扇区会亮起来，中间的圆环显示停留进度。界面上随时显示
已采样扇区数和**还缺哪些角度区间**（跨 0° 的缺口会合并成一段，不会被切开）。

采到的值**自动存盘**，转到一半退出也不会丢。

罗盘不可用时（权限被拒、没有磁力计、非 HTTPS）会退化成 36 格手动输入，
功能不缺；也可以一键「全部设为 0°」当平地处理。任何时候都能点格子手改单个扇区。

### 罗盘校正

记录里有一个「罗盘校正」字段，默认 0，会加到罗盘读数上。

iOS 的 `webkitCompassHeading` 给的是真北，通常填 0 就行。安卓等平台通过
`deviceorientationabsolute` 拿到的多半是**磁北**，悉尼磁偏角约 +12.7°E，
差这么多会让遮挡判定整体偏掉。也可以对着已知方向的建筑物标定一下再填差值。

## 太阳位置算法

`js/core/solar.js` 是 NOAA Global Monitoring Laboratory Solar Calculator
所用天文公式的本地实现（底层出处是 Jean Meeus《Astronomical Algorithms》第 2 版）。
**完全本地计算，不调任何接口**，断网可用。

### 接口约定

- 所有对外的时刻都是 **UTC epoch 毫秒**，时区只在界面层出现
- `altitude` = 几何高度角（日面中心，不含大气折射）
- `apparentAltitude` = 视高度角（含折射修正）——肉眼和手机测到的是这个
- `azimuth` = 真北起算、顺时针为正，0–360

```js
BH.Solar.position(ms, lat, lon)
  // → { altitude, apparentAltitude, azimuth, declination,
  //     hourAngle, equationOfTime, julianDay, ms }

BH.Solar.events(refMs, lat, lon)
  // refMs 传该日当地正午附近的任意时刻
  // → { solarNoon, sunrise, sunset, civilDawn, civilDusk,
  //     nauticalDawn, nauticalDusk, astronomicalDawn, astronomicalDusk }
  //   极昼极夜时相应字段为 null

BH.Solar.altitudeCrossing(refMs, lat, lon, targetAlt, rising)
  // 求任意高度角的穿越时刻，蓝调区间上下界就靠它
```

日出日落用 NOAA 的 90.833° 天顶角约定（几何高度角 −0.833°）；
各级暮光用几何高度角 −6 / −12 / −18°，与各国天文台公布值口径一致。

求根方式：先用时角公式给初值，再对几何高度角做牛顿迭代（中心差分求导），
收敛到毫秒级。比 NOAA 自己只迭代一趟的做法更准。

### 精度实测

对比 [NOAA Solar Calculator](https://gml.noaa.gov/grad/solcalc/) 公布的悉尼
（−33.8688 / 151.2093，Australia/Sydney）逐日表，选取 2025–2026 跨越四季、
两个二至、两个二分、以及**夏令时起止当天**共 16 个日期：

| 量 | 最大偏差 | 要求 |
| --- | --- | --- |
| 日出 | 29 秒 | < 60 秒 |
| 日落 | 25 秒 | < 60 秒 |
| 太阳正午 | 14 秒 | < 30 秒 |

日出日落的 16 个值**四舍五入到分钟后与 NOAA 公布值逐一相同**，
不只是落在容差内——NOAA 公布值本身就是取整到分钟的，这是能做的最严比对。

太阳正午那 14 秒不是本实现的误差。NOAA 该列的时差只迭代一趟、
取值时刻比真正的正午早约半天，在时差变化最快的十二月底会差十几秒。

交叉参考 [Geoscience Australia](https://geodesyapps.ga.gov.au/sunrise)
（GA 只接受度+整分坐标，实际用 −33°52′ / +151°12′），6 个日期 ×
日出/日落/民用晨昏/航海晨昏/中天共 42 项：偏差落在 **−2 到 +56 秒**，
且几乎全为正。这正是 GA 把秒数**截断**（而非四舍五入）到分钟的特征——
扣掉截断后，两套独立算法的实际一致性在**几秒量级**。

GA 与 NOAA 之间本身就有约 1 分钟的差异（例如 2026-06-21 日落
GA 16:53 / NOAA 16:54），因为两者用的不是同一套算法。本项目以 NOAA 为主基准。

### 一个要记住的坑

NOAA 自身有一处不自洽：日出日落用的 `90.833°` 天顶角隐含地平折射 34′（0.567°），
但它的 `calcRefraction()` 在地平线只给 0.482°。两者差 0.085°。

结果是：**日落那一刻的视高度角是 −0.436°，不是 0.000°**。
折算成时间在悉尼约 25 秒。界面上一律显示视高度角，不要把日落当成 0 度。
这条已经固化成断言写在测试里了。

## 功能二：分钟级光线时间轴

选一条勘景记录 + 一个日期，输出**从日落前 40 分钟到航海暮光结束**的逐分钟表：
时间、太阳视高度角、方位角、是否被地平线挡住、EV100、两档原生 ISO 各自需要的
T 档、天光色温。表头和时间列都吸住，默认滚到最该看的那一行
（当前分钟 → 真实日落 → 蓝调窗口开始 → 天文日落）。

### 表格怎么突出蓝调窗口，又不破坏暗适应

不是把窗口行调亮，而是**把窗口外的行压暗**：窗口外的文字降到 `--ink-faint`，
窗口内保持正常亮度，时间格左侧一条 3px 的细琥珀竖线，开始和结束各插一行标记。
整张表的总亮度是**下降**的，窗口反而跳出来了。竖线只有 3px 宽，没有大面积亮色块。

窗口里每一行**真正要用的那个数**——按当前镜头最大光圈自动选定的原生 ISO 下的
T 档——加粗成琥珀色。另外在发生的那一分钟插一行标记：

- `▾ 蓝调开始 · 太阳 0°` / `▴ 蓝调结束 · 太阳 −9°`
- `▸ 切到 ISO 3200（Canon nFD 50mm F1.4 开到头了）`——加粗的那一格会从
  T@400 列跳到 T@3200 列，一眼就能看出该在哪一分钟切原生 ISO
- `▸ 超出 T1.4，这支镜头从这里开始拍不了`

列序是「时间 | T@低 | T@高 | EV100 | 高度 | 方位 | 色温」。T 档紧跟时间，
因为它们是真正要拨到镜头上的数——原来排在高度方位后面，窄屏上切到 ISO 3200
之后，要用的那一列正好被挤出屏幕右边。

单原生 ISO 的机器（两档填一样）只显示一列 T 档，也不会报"已切到高原生 ISO"。

### 帧率和快门角度跟着勘景点走

帧率和快门角度是按镜头（shot）设计的——这个机位拍 50fps 升格、那个机位拍 24fps，
不是机器的属性。所以它们存在每条勘景记录上，在时间轴页的「拍摄参数」里直接选，
选完整张表按新的快门速度重算。

- 帧率：23.976 / 24 / 25 / 29.97 / 30 / 48 / 50 / 59.94 / 60 / 100 / 120，其余走「自定义…」
- 快门角度：45 / 90 / 144 / 172.8 / 180 / 270 / 360，其余走「自定义…」。
  172.8° 是 24fps 在 50Hz 市电（澳洲）下不闪的角度（1/50 秒），144° 是 60Hz 下的
- 没选过的记录按 24fps / 180°（1/48 秒）算

设置里的摄影机只记机器本身的能力：名称和原生 ISO。换机器只换 ISO，不动快门。

帧率和快门两个下拉在 375 宽的屏上并排一行；窄于 360（iPhone SE 1 代、开了「放大显示」
的 mini）时每个只剩 77px，放不下「23.976」「172.8°」，自动改成上下两行。

### 高度角一律用视高度角

全项目只用**视高度角**（apparentAltitude，含大气折射）这一个量：界面显示的、
遮挡判定用的、EV 和色温模型吃的、蓝调窗口边界求的都是它，不做任何暗中切换。
否则表里的读数和算出来的 T 档会对不上。

代价是：天文日落那一刻视高度角是 **−0.44°** 而不是 0.00°
（NOAA 的折射模型在地平线给 0.48°，而日落用的 90.833° 天顶角隐含 34′=0.567°，
两者不自洽）。所以 EV 锚点里的「0 度（日落）」严格说差了 0.44°，折算成 EV 约 0.4 档。
这在模型误差范围之内，也正是实测校准要吃掉的东西。低于 −3° 之后折射量已小于
0.11°，民用/航海暮光那几个锚点不受影响。

### 色温模型只在 0° 及以下有效

色温锚点只覆盖 0° 到 −12°。**不能**沿 0→−4 段的斜率往 0° 以上外推——
那一段是"太阳越低越蓝"，而 0° 以上趋势是反的（太阳升高、大气消光减少、
直射光变冷），照着外推会在日落前 40 分钟给出 1800K 这种明显错误的数。
所以 0° 以上一律返回顶端锚点 3200K，并在表里把这些格子调暗，标明超出模型范围。

如果你想让日落前那段也有意义，给我一个 +10° 左右的色温锚点（大概 4500–5000K），
我加进去。

### 档位超界要标出来，不能静默夹住

算出的 T 档超出常用档位表（1.0–22）时显示 `＞T22` 或 `＜T1`，
而不是静默夹到端点——那会让人以为 T22 拍得了，实际需要 T39。

### 真实日落

把剖面按太阳方位角插值出遮挡仰角，和太阳视高度角比较，按项目约定用**日面中心**。
遮挡发生的那一分钟高亮标出，并用相邻两分钟的余量插值到秒。

实测：西侧一片 3° 的建筑就能让日落比天文日落**早 17–20 分钟**。
遮挡越高提前越多（1°/3°/6° 依次递增），这条有测试守着。

没采剖面时不判遮挡，界面明说"还没采地平线剖面"，不假装有答案。

### 实测校准

表格里点任意一行可以记一个现场读数，存下 (太阳视高度角, 实测 EV100, 地点 id, 日期)。
抽屉里可以直接填 EV100，也可以从光圈 / 快门 / ISO 换算。

拟合的是 `实测 ≈ a × 模型 + b`（最小二乘）。取数顺序：

1. 本地点 ≥3 个点 → 用本地点拟合斜率+偏移
2. 否则全局 ≥3 个点 → 用全局拟合
3. 否则本地点 ≥1 个点 → 用本地点只求偏移
4. 否则全局 ≥1 个点 → 用全局只求偏移
5. 都没有 → 通用模型

点少时斜率容易跑飞，夹在 0.5–2.0。所有点挤在同一高度角上时解不出斜率，
退化成只求偏移。界面顶部明确显示当前是「通用模型」还是
「已用 N 个实测点校准（本地点 / 全局）」，并给出拟合式和残差。

### 补光交叉点

灯具填「在某个距离上的照度（lux）」，换算 `EV100 = log2(lux / 2.5)`，
在时间轴上标出环境光衰减到和这支灯相等的那一分钟。距离换算按平方反比。

### 窗口统计与拍摄量核算

顶部大字显示蓝调窗口时长。上下界按太阳视高度角在设置里可调，默认 0° 到 −9°。
窗口端点用牛顿迭代精确求解，不是靠逐分钟扫描凑出来的。

填入这个机位计划拍几个 setup，给出每个 setup 的平均可用时间；
低于 8 分钟时明确警告，并算出这个窗口最多排几个、建议砍掉几个。

## 功能三：七天云量决策表

用 Open-Meteo 的 forecast 接口拉未来 7 天逐小时的
`cloud_cover_low` / `cloud_cover_mid` / `cloud_cover_high` /
`precipitation_probability` / `temperature_2m`。免费，不需要 API key。
**这是整个工具唯一联网的功能**，其它部分断网照常可用。

### 按重叠时长加权，不取整点值

每天取该日蓝调窗口覆盖的那几个小时，按**与窗口的重叠时长**加权平均。
窗口通常只有四十来分钟，还常常横跨两个整点，简单取整点值会偏。

时间口径用 `timezone=UTC&timeformat=unixtime`，拿到的是干净的 epoch 秒；
蓝调窗口本来就是 epoch 毫秒，两边直接对齐，不需要解析任何时区字符串。
多拉一天（8 天）留余量，因为当地傍晚可能落在 UTC 的次日。

### 三层云分开显示

低云、中云、高云各占一列，不合并成"总云量"——低云挡光、高云出层次，
混在一起就没法判断了。低云那一列单独加重并按结论上色。

结论只看低云：低于 20% 是「好」，20–50% 是「可能」，高于 50% 是「不建议」。
高云超过 30% 额外标一句「高云可能增加天空层次」——低云好 + 高云高，
正是最想要的那种天。

### 离线

每次成功拉取都写进 IndexedDB。半小时内的缓存直接用，不重复打接口。
断网时回落到缓存，顶部明确写「缓存数据 · 获取于 X · 这次没连上：原因」。
本机连缓存都没有时如实说拿不到，并提醒其它功能不受影响。

## 日 / 夜主题与设置入口

每一页右上角有两个按钮：**设置**（滑块图标）和**日/夜切换**。设置页自己那里
不放设置按钮。从任何一页点进设置，左上角返回就回到原来那一页。

日/夜在项目设置最上面也能切。默认夜间。

- **夜间**：黄昏和夜里站在机器旁边用。背景近纯黑、暖白字、琥珀强调，不破坏暗适应。
- **日间**：白天在大太阳底下勘景用——那时候深色界面反光看不清。暖白底、近黑字，
  强调色压成深琥珀（`#ffb340` 在白底上只有 1.8:1，必须压深）。

几个实现上的点：

- **所有颜色都是 CSS 变量**，组件里一个写死的色值都不留，SVG 也改成用 class 着色。
  只有取景器那几处例外——它们叠在相机画面上，本来就该固定。
  `theme.test.js` 会读样式表逐条检查，违反了就测试失败。
- **两套主题的对比度都有测试**：直接读样式表里的变量（不在测试里再抄一份色值，
  抄了就会漂移），把界面上真实出现的 23 组文字/背景逐一算 WCAG 对比度，
  都要 ≥ 4.5:1。
- **偏好存在 localStorage，不是 IndexedDB**：主题必须在首次绘制之前定下来，
  否则每次打开都先闪一下夜间再跳日间。IndexedDB 是异步的赶不上，
  `index.html` 的 `<head>` 里有一小段同步脚本在样式表之前读它。
  这是界面偏好，不跟着 JSON 导出走。
- **iOS 状态栏**：`apple-mobile-web-app-status-bar-style` 用的是 `black-translucent`
  （夜间最好），但它只在启动时读、字永远是白的。日间的浅色顶栏会让时间和电量
  直接看不见，所以日间把刘海安全区那一条单独涂深。没有刘海的设备上这条自动消失。

## 界面优化（第二轮）

逐屏审查后改了这些：

**真 bug**

- **iOS 上输不了负数。** 所有数字框原来都是 `type="number"` + `inputmode="decimal"`，
  而 iOS 的 decimal 小键盘上**没有负号**。纬度、经度、罗盘校正、剖面格子、
  蓝调区间下界（默认就是 −9°）、实测 EV100——六处全都输不了负数，
  **在悉尼连自己的纬度都填不了**。现在统一用 `A.numInput()`：
  `type="text"`（这样单独一个负号才留得住）、有正负号的字段旁边带 ± 键、
  逗号小数点和 Unicode 减号都能认。
- **设置页八个「删除这支」点了直接删**，没有确认，而且就排在滚动路径上。
  现在删除收进编辑抽屉并且要二次确认。

- **iOS 键盘会盖住底部抽屉**（剖面格子手填、记录实测都在抽屉里输数字）。
  现在用 `visualViewport` 量出键盘高度，抽屉整体上移。

**好用程度**

  「今晚蓝调 17:51–18:32 · 41 分钟」和真实日落；今晚已经过了就给明晚，
  正在进行就写「正在进行」。
- **记录概览**填完之后，顶部不再说"这条记录已经够用了"（没有信息量），

- **七天云量**：顶部加一条一周总览，七天的结论（圆点颜色）和低云百分比并排，
  点某天跳到详情。原来七张卡一屏只放得下三张，"哪天能拍"要滚完整页才知道。
- **设置页**从 3.6 屏的表单墙改成「摘要行 + 点开编辑」，降到 2.06 屏。
- **摄影机改成列表**，和镜头、灯具一样可以加多台、选一台在用。每台只记名称和

  每个都是一小块亮色，违背暗适应的原则；而且 ☀ 在圆形徽章里小到几乎看不见。

## 边界条件审查

三个功能做完后做了一轮专项审查。`js/test/edge.test.js` 不测"正常情况对不对"，
只测"特定条件下会不会炸或者悄悄给出错误结果"：夏令时起止两天、跨年、闰日、
非闰年的 2/29、赤道、对跖经线 ±180、北半球、极昼极夜、帧率为 0 或乱填、没有镜头、
selectedLens 越界、蓝调区间上下界相等（除零）、setup 数为 0 / 负 / 999、
照度为 0 / 负 / 1e12、剖面只有一个点 / 全为负值 / 带 ±89°、时区无效、
以及把各种垃圾喂给三个 `normalize()`。最后还有一遍
「2026 全年 × 四个纬度、上千个数值全部必须有限」的 NaN 泄漏扫描。

这一轮查出来的问题：

**1. `setups` 的取值规则藏在界面层。** 记录和项目设置里都有 `setups`，
但 `Timeline.build()` 只读 `settings.setups`，"记录优先"的合并写在 `timeline-ui` 里。
别的调用方会静默拿错值。已把规则挪进 `core/timeline.js`。

**2. 改 setup 数时会丢输入焦点。** 原先每次 `input` 都整页重建，而重建会把
输入框本身销毁重建，焦点随之丢失——想输两位数只能输进第一位。
已把拍摄量核算抽成纯函数 `TL.budgetFor()`，就地更新，不再整页重建。

**3. 迟到的异步回调会顶掉当前页。** `setTop` / `setDock` 写的是全局顶栏和底栏，
一个已经离开的页面，其异步回调返回时会把**当前**页的顶栏底栏顶掉。
已给所有迟到回调补上 `disposed` 守卫（`settings-ui` 和列表页原先根本没有这个标记）。

**4. 最严重的一条：授权对话框迟到会把相机留在开着。** 点「启用罗盘和相机」
之后立刻返回，iOS 的授权弹窗仍在，等它返回时页面早已销毁，`vf.start()` 照样成功——
相机开着、指示灯常亮，而且再没人去关它。已在回调里加了
`if (disposed) { vf.stop(); return; }`。

**5. 测试框架自己会撒谎。** 抛错的测试只记在 `t.failed` 上、不计入失败总数，
于是"一条断言都没跑到就挂了"的测试会被汇总成 `failed: 0`，整页报「全部通过」。
这是最危险的一类：测试在爆炸，报告却是绿的。已修，并补了自检——
现在抛错会计入失败并单独标出「其中 N 个测试直接抛错」。

修完这条之后立刻抓到一个真实的漏配：`test.html` 少引了
`records.js` 和 `settings.js`，导致 4 个边界测试一直在静默抛错。

## iOS 上的几个坑（都已在代码里处理）

1. **必须 HTTPS。** Geolocation 和 DeviceOrientation 在 iOS 上都要求安全上下文，
   而且 `localhost` 不算数——这一点和桌面浏览器不同。见下一节。
2. **iOS 13+ 必须先调 `DeviceOrientationEvent.requestPermission()`**，而且
   **只能在用户手势的同步回调里**调，页面加载时调会抛 `NotAllowedError` 或者
   静默失败。所以界面上有一个明确的「启用罗盘」按钮，`js/ui/compass.js`
   只暴露 `request()`，由那个按钮触发。
3. **真北方位角在 `event.webkitCompassHeading`，不在 `alpha`。**
   iOS 的 `alpha` 是相对起始姿态的，当罗盘用会错得离谱。
   安卓路径走 `deviceorientationabsolute`，并且只认 `absolute === true` 的事件。
4. **权限被拒绝有完整降级路径**：剖面页退化成 36 格手动输入，
   机位朝向可以直接键入，功能不缺。状态提示会说清楚是哪种情况、怎么恢复。
5. **从主屏幕启动的实例和 Safari 里的实例，存储不共通**，权限也要各自授权一次。
6. **未安装到主屏幕的站点，Safari 有 7 天未访问清除本地存储的策略。**
   添加到主屏幕之后不受这条影响。重要记录建议定期导出 JSON 备份。
7. 输入框字号统一 16px，否则 iOS Safari 聚焦时会自动放大页面。

## 本地 HTTPS 调试

iOS 上 Geolocation 和 DeviceOrientation **必须 HTTPS**，`localhost` 不算数
（这一点和桌面浏览器不同，桌面把 localhost 当安全上下文，iOS Safari 不）。
所以要在 iPhone 上调罗盘和定位，只有两条路。

### 路线 A：直接推 GitHub Pages 测（推荐）

改完就 push，一分钟后在 iPhone 上刷新。省掉证书那一堆事，
也最接近最终运行环境。手机不用和电脑在同一个网络，用蜂窝数据也行。
日常迭代建议走这条。具体命令见下面「部署到 GitHub Pages」一节。

**在 iPhone 上要验的四件事：**

1. 打开站点 → 新建一条记录 → 点「一键获取当前位置」。
   应该弹出定位授权，允许后填入坐标并显示精度（室外通常 ±5–20 m）。
2. 进「采集地平线剖面」→ 点**「启用罗盘」**。
   应该弹出 iOS 的「允许访问运动与方向」对话框。
   这一步如果没弹窗、也没反应，八成是没走 HTTPS。
3. 竖着举手机，用**背面**对准前方，左右转一下：
   罗盘图中间的大数字应该跟着变，指针跟着转。
   把手机往上抬，仰角应该变正；往下压，变负。
   **对着一个已知方向验一下**（比如正对某条南北向的街），
   读数不对就说明要填「罗盘校正」。
4. 原地**缓慢**转一圈，每个方向停半秒左右。

### 离线缓存为什么是网络优先

Service Worker 最初用的是 stale-while-revalidate（先给缓存、后台更新）。
那个策略有个要命的毛病：**浏览器只在 `sw.js` 自身字节变化时才认为 SW 有更新**。
只改业务代码、不动 `sw.js` 的那种发布，既不会弹「有新版本」，也会继续把
缓存里的旧代码喂出来——改完推上去，打开还是旧的，还以为没生效。

现在是**网络优先、缓存兜底**（2 秒超时）：

- 有网就一定拿最新的；网络失败或 2 秒没响应才退回缓存
- 完全断网时 `fetch` 会立刻拒绝，不会真等 2 秒，离线体验不受影响
- 这些文件只有几十 KB，多一个往返换"改完就生效"，值

还有一个坑单独说：**SW 里的 `fetch(req)` 仍然会命中浏览器自己的 HTTP 缓存**。
GitHub Pages 会发 `Cache-Control: max-age=600`，python 的 `http.server` 只发
`Last-Modified` 让浏览器启用启发式新鲜度——两种情况下 `fetch` 都可能压根不碰
网络，"网络优先"就成了空话。所以 SW 里用 `cache: 'no-cache'` 强制带条件头回源，
文件没变时服务器回 304，很便宜。

另外 `install` 里**不**调 `skipWaiting()`：新版本先进入 waiting，由页面弹
「有新版本 / 刷新」让你自己决定何时切。现场可能正在转圈采集剖面，
突然重载会把罗盘和相机权限一起丢掉。反正业务代码走网络优先，
SW 自身晚一点换没代价。

列表页右上角「数据」里能看到当前缓存版本，还有一个「检查更新」按钮——
缓存陈旧最麻烦的地方是它不可见，所以把它摆出来。
